## Overview

**SmartGas** is a comprehensive gas cylinder inventory and lifecycle management system designed for hospital logistics pharmacy operations. It enables staff to:

- Track each individual gas cylinder in real-time across the entire hospital
- Issue cylinders to wards and units using a wireless 2D barcode scanner
- Receive returned empty cylinders back from wards
- Send empty cylinders to the concessionaire (**Gas Pantai Timur Sdn Bhd — GPT**) for refilling
- Receive freshly refilled cylinders from GPT and register them into inventory
- Print QR/barcode labels (thermal transfer) for new cylinders
- Generate inventory reports and view transaction history

Every cylinder is identified by a unique scannable **Gas ID** (e.g., `ox0.5pi1`, `ca7.0bn2`) that encodes the gas type, volume, and valve type, making bulk scanning fast and unambiguous.

## Features

### Scanner Page (Home)
- **Always-listening** scanner input — captures scanned barcodes instantly without any button click
- Multiple operation **tabs**: Issue, Return, Return to GPT, Receive from GPT
- Real-time cylinder validation on scan (checks status, existence, location)
- Scanned list accumulates for bulk submit
- Prominent success/failure flash messages after each transaction
- Audio feedback on scan success, duplicate, and error events

### Inventory Page
- Full cylinder inventory with multi-column **search, filter, and sort**
- Filter by: Gas Type, Volume, Valve Type, Status, Location, Hospital/Vendor
- Inline **edit** cylinder status, location, batch number, expiry date, notes
- **Print label** shortcut directly from inventory row
- Pagination with configurable page size

### Register Cylinder Page
- Manual form to register individual cylinders
- Auto-generates Gas ID from type + volume + valve type (e.g., `ox0.7bn3`)
- Auto-generates display name (e.g., `Oxygen 0.7 m³ Bullnose`)
- Defaults to Logistic Pharmacy as the initial location and `Full` as status

### Label Registration Page
- **Bulk label generation** preview — generates a batch of sequential Gas IDs without committing to database
- Live barcode/QR code rendered via **JsBarcode**
- Configurable quantity and batch number
- Optimized for **thermal transfer label printing** (Zebra ZD420 or equivalent)
- Supports registering cylinders into DB directly from the label preview

### Reports Page
- Transaction history filtered by date range, type, location, and gas type
- Summary aggregations (total issued, returned, at vendor)
- Printable / exportable views

### Settings Page
- Full **CRUD** for all reference/lookup tables:
  - Gas Types (code, name, color badge)
  - Gas Volumes (value, unit, display label)
  - Valve Types (code, name)
  - Cylinder Statuses (code, name, badge color)
  - Hospital Locations / Wards
  - Vendors / Concessionaires
- **Drag-to-reorder** with persistent sort order saved to database
- Toggle **active/inactive** status for any reference item

## System Workflows

### 1. Issue Gas to Ward / Unit
```
Staff selects "Issue" tab
  → inputs Indenter name & destination ward
  → scans each cylinder QR/barcode
  → system validates each scan (exists? correct status?)
  → staff confirms list vs. indent form
  → system commits:
      status → ISSUED
      location → destination ward
      transaction record created (ISSUE-YYYYMMDD-####)
  → success screen → resets for next transaction
```

### 2. Return Empty Cylinders from Ward
```
Staff selects "Return" tab
  → inputs returner name
  → scans each cylinder QR/barcode
  → system lists items with default status: EMPTY
  → staff can override per item (Expired, Damaged, etc.)
  → staff confirms list
  → system commits:
      status → EMPTY / EXPIRED / etc.
      location → Logistic Pharmacy
      transaction record created (RET-YYYYMMDD-####)
```

### 3. Return to GPT (Vendor) for Refilling
```
Staff selects "Return to GPT" tab
  → inputs optional Delivery Order No.
  → scans each empty cylinder
  → confirms list
  → system commits:
      status → RETURNED_TO_VENDOR
      location → Gas Pantai Timur (offsite, not in hospital)
      transaction record: VEND-RET-YYYYMMDD-####
```

### 4. Receive Refilled Cylinders from GPT
```
Staff selects "Receive from GPT" tab
  → inputs DO No. and batch number
  → scans existing cylinder QR (if sticker present)
    OR registers new cylinder + prints label
  → system sets:
      status → FULL
      location → Logistic Pharmacy
      new cylinders get sequential Gas IDs
      transaction record: RECEIVE-YYYYMMDD-####
```

### 5. Viewing & Managing Inventory
```
Inventory Page
  → filter/search/sort by any attribute
  → individual cylinder location visible at all times
  → inline status / location edit
  → quick-print label from any row
  → hospital-wide cylinder tracking in real-time
```

## Database Schema

The PostgreSQL schema consists of **10 tables**, **4 views**, **8 triggers**, and **12 performance indexes**.

### Core Tables

| Table                | Purpose                                                           |
|----------------------|-------------------------------------------------------------------|
| `gas_types`          | Reference: Gas types (Oxygen, CO₂, etc.) with color codes        |
| `gas_volumes`        | Reference: Available sizes (0.5 m³, 6 KG, etc.)                  |
| `valve_types`        | Reference: Valve configurations (Pin Index, Bullnose, Ambulance)  |
| `cylinder_statuses`  | Reference: Lifecycle statuses (Full, Issued, Empty, etc.)         |
| `vendors`            | Concessionaire/refiller companies (e.g., Gas Pantai Timur)        |
| `locations`          | Hospital wards, units, and offsite vendor sites                   |
| `users`              | System users with roles (`admin`, `staff`, `viewer`)              |
| `gas_cylinders`      | **Core asset table**: every individual cylinder with its Gas ID   |
| `transactions`       | Transaction header (ISSUE, RETURN, RETURN_TO_VENDOR, RECEIVE, ADJUSTMENT) |
| `transaction_items`  | Per-cylinder line items with before/after status snapshots (audit trail) |

### Database Views

| View                    | Purpose                                              |
|-------------------------|------------------------------------------------------|
| `v_cylinder_details`    | Fully joined cylinder view with all resolved names   |
| `v_hospital_inventory`  | Cylinders physically inside the hospital only        |
| `v_cylinders_at_vendor` | Cylinders currently offsite at GPT for refilling     |
| `v_inventory_summary`   | Aggregated counts by location, type, and status      |

### Cylinder Status Lifecycle

```
  New Registration
        │
        ▼
     [FULL] ◄────────────────────────────────────────┐
        │                                             │
    Issue to Ward                          Receive from GPT
        │                                             │
        ▼                                             │
  [ISSUED / IN-USE]                    [RETURNED_TO_VENDOR]
        │                                             ▲
    Return from Ward                    Return to GPT │
        │                                             │
        ▼                                             │
     [EMPTY] ──────────────────────────────────────► ┘
        │
        ├──► [EXPIRED]
        ├──► [DAMAGED]
        └──► [MAINTENANCE]
```

### Transaction Number Format

| Type                | Prefix       | Example                  |
|---------------------|--------------|--------------------------|
| Issue to Ward       | `ISSUE-`     | `ISSUE-20261013-0001`    |
| Return from Ward    | `RET-`       | `RET-20261013-0001`      |
| Return to Vendor    | `VEND-RET-`  | `VEND-RET-20261013-0001` |
| Receive from Vendor | `RECEIVE-`   | `RECEIVE-20261013-0001`  |
| Inventory Adj.      | `ADJUST-`    | `ADJUST-20261013-0001`   |

All numbers are zero-padded 4-digit sequential per prefix per day (e.g., `-0001`, `-0002`).

## Label Printing System

### Recommended Specifications

| Component          | Specification                                                        |
|--------------------|----------------------------------------------------------------------|
| **Label Stock**    | Polyester (PET) peel-and-stick — chemical & abrasion resistant       |
| **Printing Method**| Thermal transfer with Resin Ribbon (heat, chemical, scratch resistant) |
| **Overlaminate**   | Clear label protectors / heavy-duty packing tape                     |
| **Printer**        | Zebra ZD420 or Toshiba TEC thermal transfer printer                  |

### Labeling Strategy (Option 2 — Unique ID per Cylinder)

- Each physical cylinder gets a **permanently unique Gas ID sticker**
- Cylinders of the **same type** can have stickers swapped if needed (e.g., `ox0.7bn1` ↔ `ox0.7bn2`)
- Labels can be **pre-printed in bulk** and kept on standby — applied when new cylinders arrive from GPT
- New cylinder arrivals without stickers: create a record → print label → apply → scan to confirm receipt

```
 Apache HTTPD  (port 80 / 443)
      │
      ├─── /gas  ──────────────►  dist/  (static React build, served directly)
      │
      └─── /api  ──────────────►  ProxyPass → http://localhost:3009  (Fastify via PM2)
```

### Step 2 — PM2 (Backend Process Manager)

Install PM2 globally on the server:

```bash
npm install -g pm2
```

Create `backend/ecosystem.config.js` in the project:

```js
// backend/ecosystem.config.js
export default {
  apps: [
    {
      name: 'smartgas-api',
      script: './backend/server.js',

      // Run from project root so relative paths resolve correctly
      cwd: 'D:/dev/storgas',

      // Use Node.js ESM (required — package.json has "type": "module")
      interpreter: 'node',
      interpreter_args: '--experimental-vm-modules',

      instances: 1,           // Single instance (scale up if needed)
      exec_mode: 'fork',      // 'cluster' mode requires ESM-compatible PM2 v5+

      watch: false,           // Disable in production (use CI/CD for restarts)
      autorestart: true,
      max_restarts: 10,
      restart_delay: 3000,    // ms between auto-restarts

      env: {
        NODE_ENV: 'production',
        PORT: 3009,
      },

      // Logging
      out_file: './logs/api-out.log',
      error_file: './logs/api-error.log',
      log_date_format: 'YYYY-MM-DD HH:mm:ss Z',
      merge_logs: true,
    },
  ],
};
```

> Create the `logs/` directory first: `mkdir D:\dev\storgas\logs`

**PM2 Commands:**

```bash
# Start / restart using ecosystem file
pm2 start backend/ecosystem.config.js

# Check status
pm2 status

# View live logs
pm2 logs smartgas-api

# Reload without downtime (when ecosystem.config.js updated)
pm2 reload smartgas-api

# Save process list so it survives reboots
pm2 save

# Register PM2 as a Windows startup service (run as Administrator)
pm2-startup install
# -- or on Linux/macOS:
pm2 startup
pm2 save
```

### Step 3 — Apache VirtualHost Configuration

Enable required Apache modules first:

```bash
# Linux (Debian/Ubuntu)
sudo a2enmod proxy proxy_http rewrite headers

# Windows XAMPP / manual Apache: uncomment in httpd.conf:
# LoadModule proxy_module modules/mod_proxy.so
# LoadModule proxy_http_module modules/mod_proxy_http.so
# LoadModule rewrite_module modules/mod_rewrite.so
# LoadModule headers_module modules/mod_headers.so
```

**VirtualHost config** (HTTP — add to `httpd.conf` or a dedicated `.conf` file in `conf/extra/` or `/etc/apache2/sites-available/`):

```apache
<VirtualHost *:80>
    ServerName  yourhospital.local
    # ServerName  192.168.1.100      # or IP address for LAN-only deployments

    # ── Frontend: React Static Build ────────────────────────────────────
    # Serve the Vite build output at /gas
    Alias /gas "D:/dev/storgas/dist"

    <Directory "D:/dev/storgas/dist">
        Options -Indexes +FollowSymLinks
        AllowOverride None
        Require all granted

        # SPA fallback: any sub-path under /gas that is not a real file
        # gets rewritten to /gas/index.html so React Router handles it
        RewriteEngine On
        RewriteBase /gas/
        RewriteCond %{REQUEST_FILENAME} !-f
        RewriteCond %{REQUEST_FILENAME} !-d
        RewriteRule ^ index.html [L]
    </Directory>

    # ── Backend: Fastify API Reverse Proxy ───────────────────────────────
    # All /api/* requests are forwarded to the PM2-managed Fastify server
    ProxyPreserveHost On

    ProxyPass        /api  http://127.0.0.1:3009/api
    ProxyPassReverse /api  http://127.0.0.1:3009/api

    # Forward real client IP to Fastify
    RequestHeader set X-Forwarded-For "%{REMOTE_ADDR}e"
    RequestHeader set X-Forwarded-Proto "http"

    # ── Logging ──────────────────────────────────────────────────────────
    ErrorLog  "D:/dev/storgas/logs/apache-error.log"
    CustomLog "D:/dev/storgas/logs/apache-access.log" combined
</VirtualHost>
```

**Optional — HTTPS VirtualHost** (requires mod_ssl and a certificate):

```apache
<VirtualHost *:443>
    ServerName yourhospital.local

    SSLEngine on
    SSLCertificateFile    /path/to/cert.pem
    SSLCertificateKeyFile /path/to/key.pem

    Alias /gas "D:/dev/storgas/dist"
    <Directory "D:/dev/storgas/dist">
        Options -Indexes +FollowSymLinks
        AllowOverride None
        Require all granted
        RewriteEngine On
        RewriteBase /gas/
        RewriteCond %{REQUEST_FILENAME} !-f
        RewriteCond %{REQUEST_FILENAME} !-d
        RewriteRule ^ index.html [L]
    </Directory>

    ProxyPreserveHost On
    ProxyPass        /api  http://127.0.0.1:3009/api
    ProxyPassReverse /api  http://127.0.0.1:3009/api

    RequestHeader set X-Forwarded-For "%{REMOTE_ADDR}e"
    RequestHeader set X-Forwarded-Proto "https"

    ErrorLog  "D:/dev/storgas/logs/apache-ssl-error.log"
    CustomLog "D:/dev/storgas/logs/apache-ssl-access.log" combined
</VirtualHost>
```

Restart Apache after saving the config:

```bash
# Linux
sudo systemctl restart apache2

# Windows XAMPP
httpd -k restart

# Windows service
net stop Apache2.4 && net start Apache2.4
```

**Access the application at:** `http://yourhospital.local/gas`
